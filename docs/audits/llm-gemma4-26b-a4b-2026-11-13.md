# Gemma 4 26B A4B の評価（2026-11-13）

前提の調査: `docs/audits/llm-candidates-2026-10-28.md`（同じ評価一式と方法）。本番の LLM は切り替えていない。

## 結論

- **本番の枠（`--gpu-memory-utilization 0.55`、`--max-model-len 16384`）には 4 bit 版が入る。Tokkio の GPU0 一式（sokutou、ASR、A2F、Triton、この LLM）も同時に載る。ただし空きは約 4 GB で、余裕は小さい。**
  - `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit` は、vLLM 0.32.0 でそのまま起動した（重み 15.56 GiB、KV キャッシュ 8.13 GiB = 103,148 トークン、16,384 トークンの会話 6.3 本分）。
  - コンテナの GPU0 使用量は 26.1 GB。Tokkio が動く GPU0 全体では 45.3 GB / 49.1 GB（LLM 以外が 19.0 GB）。
- **Gemma 12B（FP8）から替える利点は小さく、今は替えなくてよい。26B は知識と生成速度で上回るが、本番相当の品質は同等である。**
  - 本番相当の盲検（4 構成を同時に再採点）: 26B 4 bit が 4.11、Gemma 12B bf16 が 4.11、12B FP8 が 4.00、Swallow が 2.78。26B と 12B の差は採点のぶれの範囲に収まる。使えない応答は 26B 6、12B 4、12B FP8 5、Swallow 29（63 問中）。
  - 知識（JMMLU）は 26B が 0.765 で、12B FP8 の 0.716 より 0.05 高い。読解（JSQuAD 完全一致）は 0.803 で、12B FP8 の 0.830 より少し低い。
  - 生成は 154 tok/s で、12B FP8（52 tok/s）の約 3 倍、Swallow（49 tok/s）の約 3 倍。応答完了までの中央値は 0.18 秒（12B FP8 は 0.55 秒、Swallow は 1.16 秒）。MoE（活性 4B）なので、重みは大きくても読み出す量が少ない。
  - 欠点: 4 bit 量子化の品質は FP8 より不確かで、盲検の使えない応答は 12B より 2 件多い。作り話と、長い応答（100 字超が 126 件中 7）が残る。
- **Swallow からの入れ替えとしては、26B 4 bit は 12B FP8 と同等以上の選択肢になる。** 12B FP8 に決めた 10-28 の判断は、26B を足しても変わらない。遅延を最優先にするか、知識の差を取るなら 26B 4 bit にする価値がある。
- 質問が短いときの最初の文字までの時間（TTFT）は、26B 4 bit で中央値 0.03 秒、95 パーセンタイル 0.05 秒（共通プロンプトのキャッシュなしでも 0.06 / 0.08 秒）。フィラーのしきい値の根拠には、後述の表を使う。

- 4 bit 版に `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit` を選んだ理由: ダウンロード数が最も多く（約 123 万）、サイズ 17.2 GB で枠に入り、vLLM 0.32.0 がそのまま読んだ（compressed-tensors の W4A16 用 Marlin カーネルと MoE 用の Marlin エキスパート）。Ada の RTX 6000 でも動く。`cyankiwi/...-qat-AWQ-INT4`（QAT のモデルを量子化、同じ 17.2 GB）と `amd/...-w4a16-llmcompressor`（15.7 GB）は、1 つ目が動いたので試していない。QAT 版は品質が上がる可能性がある。
- NVFP4 版は RTX 6000 Ada で動かないので扱っていない。
- FP8 版は重みが 28.7 GB あり、GPU0 の空き（約 30 GB）には KV キャッシュの分が入らない。重み 8 GiB を CPU メモリに載せて起動した。CPU 側の転送で遅くなるので、品質の参照にだけ使い、遅延は測っていない。

## 調べ方

10-28 と同じ評価一式（`/data/ACE/llm-eval/`）を使い、生成結果とスクリプトは `/data/ACE/llm-eval/2026-11-13-gemma26b/` に置いた。

- 生成設定は本番（`nvidia_model_input_params`）と同じ。温度 0.1、top_p 0.95、top_k 64、`max_tokens` 512、`enable_thinking: false`。Gemma 4 のチャットテンプレートは `enable_thinking` を指定しなければ思考オフ（186 行目 `default(false)`）で、思考オフの要求でも思考欄は空だった。
- 本番相当 63 問 × 2 回、JMMLU（1,120 問、10-28 の 12B FP8 と同じキー）、JCommonsenseQA（1,119 問）、JSQuAD（300 問）、JCQA の記号だけ答える指示（100 問）、ELYZA-tasks-100（生成のみ）。
- 盲検の再採点: 前回と同じ観点表（`judge/RUBRIC_persona.md`）で、Swallow（`temperature 0.6`、transformers の 10-28 の応答）、12B bf16、12B FP8、26B 4 bit の 4 つを 1 問ずつラベルを入れ替えて並べ、サブエージェント 3 つで採点した。採点セッションが違うので、10-28 の絶対値とは比べない。同じ回の相対比較だけを読む。
- 遅延は、同じ GPU0 に 1 つずつサーバーを立て、本番相当 63 問を 1 件ずつストリーミングで送った（`scripts/ttft_short.py`）。共通のシステムプロンプトのキャッシュの状態を 3 通りに分けた。
  - `tail`: 繰り返しごとに質問の末尾へ見えない文字を足すだけ。ほぼ全体がキャッシュに当たる最良の場合。26B は 5 回（315 件）、ほかは 2 回（126 件）。
  - `cold_user`: 質問の先頭に乱数を入れる。共通のシステムプロンプトだけがキャッシュ、会話・参考情報・質問は毎回新しい。本番の実際に近い。
  - `cold_all`: システムプロンプトの先頭に乱数を入れる。キャッシュなしの最悪の場合。
- 短い質問は、最後のユーザー発話が 25 字以内で参考情報のブロックがない 13 問（× 繰り返し）。
- 測定の時間帯: ほかの TTS 評価（`cap_eval.py`）が 16:00 に終わってから測った（測定前後に `ps` で動いていないことを確認）。モデルの精度の測定中は動いていたが、遅延の数字は使っていない。

### 知識・読解

- JMMLU は 26B 4 bit が 0.765。10-28 の最高だった Qwen Flash（0.81）と Qwen 27B（0.755）の間。JMMLU の選択肢記号は 98%、JCQA は 99.7% で、最初のトークンが記号だった。
- JSQuAD の完全一致は 26B が 0.803 で、12B FP8 より 0.027 低い。答えを含む割合は 0.937 で同等。答えの切り出しが少し長いことによる差とみられる（答えの字数の中央値 6、12B FP8 は 5.5）。
- ELYZA は生成だけ行い、採点はしていない（応答の字数の中央値は 26B 4 bit が 631.5、12B bf16 が 587）。

- `cold_all`（キャッシュなし）は 26B 4 bit だけ測った。
- 10-28 の 12B FP8（GPU1、0.07 / 0.24 秒、完了 0.56 秒）と今回の GPU0（0.052 / 0.237 秒、完了 0.55 秒）はほぼ同じ。

## 本番に入れる場合

- 起動定義は `infra/llm/docker-compose.gemma4-26b-a4b.yml`（既定は port 8019、コンテナ名 `ace-vllm-gemma4-26b-a4b`、モデルは HF キャッシュ `/data/ACE/hf-cache` から読む）。本番に入れるときは `VLLM_PORT=8011` を指定し、先に Swallow のコンテナを止める。手順は 12B と同じ（`infra/tokkio/README.md`）。この文書では README を変えていない。
- 起動に使った環境変数は `VLLM_GPU_DEVICES` に GPU0 の UUID を指定した。起動は約 2 分（モデルの読み込み 20 秒、`torch.compile` 76 秒、CUDA グラフ 22 秒）。
- 配信名 `gemma-4-26b-a4b-it` は `nvidia_model_input_params` の既存の `gemma-4` の判定に当たり、12B と同じ生成設定（温度 0.1、top_p 0.95、top_k 64、最大 512 トークン、思考オフ）が送られる。新しい分岐は足していない。`infra/tests/test_tokkio_llm_config.py` の `test_gemma4_uses_the_evaluated_sampling_without_thinking` に、`gemma-4-26b-a4b-it` と `google/gemma-4-26B-A4B-it` を足した。
- テスト: `python3 -m unittest infra.tests.test_tokkio_llm_config` は 67 件中 2 件が失敗した。失敗は `test_custom_config_yaml_uses_early_cached_filler_delay` と `test_custom_config_yaml_uses_nemotron_ultra_nim_endpoint_and_model` で、設定 YAML の `time_delay` とモデル名を見るテスト。今回の変更の範囲外（作業ツリーにある別の変更による）。Gemma のテスト（`-k gemma4`）は通る。
- 本番の `.env`、Tokkio、TTS、ASR には触れていない。

## 未確認・限界

- 4 bit 版（PTQ の AWQ）の品質は、FP8 の参照との比較で JMMLU・JCQA・JSQuAD のみ確かめた。本番相当の盲検は 4 bit 版だけ採点し、FP8 版の応答は採点していない（字数と 100 字超の数だけ見た）。
- 盲検の採点者は Claude（サブエージェント）で、人の採点ではない。採点セッションが 10-28 と違うため、絶対値は比べられない（Swallow は 10-28 の 3.10 に対し今回 2.78、12B bf16 は 3.97 に対し 4.11）。
- 本番相当は 63 問で、カテゴリ別は 1〜6 問。差は傾向として読む。
- 遅延は 1 件ずつ送った場合の値。同時接続時の値は測っていない（KV の 6.3 本分が上限の目安）。TTS が先に読み始める句の長さや、Tokkio を通した会話は試していない。
- `tail` の繰り返しは、質問の末尾に見えない文字（U+200B）を足してキャッシュの当たり方を変えた。出力は少し変わりうる。
- 26B FP8 は CPU オフロードで動かしたので、遅延は測っていない。
- `tokkio_params_probe.py` は走らせていない。ただし、検証した要求は `nvidia_model_input_params` の戻り値と同じ値で組んだ。
- QAT 版と AMD 版は試していない。QAT 版を試す価値はある。
- ELYZA の採点、`cold_all` での Swallow と 12B FP8、26B の同時接続は未実施。
- 12B FP8 の遅延は、10-28 の準備どおりの compose（port だけ 8019）で、今回の同じ日に測った。

# 会話の間合いの作り直し（言い終わり判定・割り込み・話し方、オフライン）

実施日: 2026-11-13 / 対象: `ace_kagawa`

目的: Tokkio のアバターとの会話を人どうしの会話に近づけるため、言い終わりの判定、割り込みの扱い、返答の話し方を作り直し、オフラインで確かめる。本番には配備していない。実マイクでは一度も確かめていない。

## 結論

3 つの動きを実装し、それぞれを `infra/tokkio/.env` のスイッチで切り替えられるようにした。既定はどれも off で、off のときのパイプラインと設定値は今の本番と同じになる。

| スイッチ | 既定 | on にしたときの動き | オフラインの結果 |
| --- | --- | --- | --- |
| `TOKKIO_TURN_END=text` | `vad` | VAD は 0.2 秒で止まり、文字起こしの文末で言い終わりを判定する。アバターが声を出す前に来訪者が話を続けたら、応答を取り消して 1 つの発話にまとめる | 来訪者の質問 160 本で、判定までの時間は p50 0.63 → 0.22 秒。途中で切った発話は 11 → 6 本 |
| `TOKKIO_BARGE_IN=gated` | `immediate` | アバターが話している間は、相づち（うん、はい）と雑音では止まらない。それ以外の発話では止まる | pipecat 0.0.68 の実物のパイプラインで動きを確かめた。止まるまでの時間は実マイクで測る必要がある |
| `TOKKIO_SPOKEN_STYLE=on` | `off` | 人物設定のプロンプトに、話し言葉で答える指示を足す | 本番の LLM で 24 問。断る・答えるの判断は 24 問とも同じ。文末が「〜ですよ」「〜ですね」になった返答は 0 → 7 問 |

- 既定を off にした理由は 2 つある。実マイクで確かめていないこと、そして `manage_tokkio.sh start` が毎回このリポジトリから設定を作り直すため、既定を on にすると次の起動で確かめていない動きが本番に入ることである。
- アバターから相づちを打つ機能は実装していない。設計の検討だけを 5 節に書いた。
- 応答の遅れのうち、LLM の最初の句までの時間はすでに 0.04〜0.19 秒で、プロンプトで縮める余地はほとんどなかった（4 節）。

## 1. 実装したもの

### 1.1 文末で言い終わりを判定する（`TOKKIO_TURN_END=text`）

`infra/tokkio/tokkio_turn.py` の `TurnGate` を、STT とユーザー側の集約器の間に入れる。VAD が 0.2 秒の無音で区切るたびに、そこまでの文字起こしの文末を 3 種類に分ける。

| 文末 | 例 | LLM に渡す時点 |
| --- | --- | --- |
| 丁寧な文末、終助詞 | です、ます、ください、か、ね、よ | すぐ（無音 0.2 秒＋認識の時間） |
| 普通形、短い返事 | 〜た、〜る、〜い、はい、いいえ、こんにちは | 無音が 0.6 秒になったとき（`turn_end_weak_wait_s`） |
| 続きがある形 | の、を、けど、えっと、読点、「そうですね」「すみません」 | 無音が 0.8 秒になったとき（`turn_end_max_wait_s`） |

2026-11-02 の規則（`turn-end-text-2026-11-02.md` の `lex`）からの変更点は次のとおり。

- 普通形と短い返事を、すぐ渡す側から 0.6 秒待つ側へ移した。11-02 の評価で切った 14 本のうち 11 本が「はい｜お願いします」のように短い返事のあとに続ける発話で、2 本が名詞を修飾する「た」だったためである。0.6 秒は今の VAD の停止と同じ長さなので、この種類の発話が渡る時点は今とほぼ同じになる。違いは 2.2 節の「渡してすぐ取り消す」の行に書いた。
- 「こんにちは」「こんばんは」「どうも」を、末尾の「は」「も」より先に短い返事として調べる。
- カタカナをひらがなにしてから判定する（Haas は「ハイ」と書くことがある）。
- 「そうですね」「すみません」を、続きがある形として扱う。返事の「そうですね。」は 0.8 秒待つことになる。すぐ答えさせたいときは、config.yaml の `turn_end_hold_phrases` から外す。

取り消しと結合は次のように動く。

- ターンを LLM に渡したあと、アバターの声が出る前（`BotStartedSpeakingFrame` の前、かつ 2.0 秒以内）に来訪者が話し始めると、pipecat の割り込みが LLM と TTS を止める。`TurnGate` は渡した文字起こしを LLM の履歴から外し、次の文字起こしと合わせて 1 つのターンとして渡し直す。取り消された応答が履歴に残した断片も外す。
- 話し始めたのが雑音で、文字起こしが空だったときは、VAD の停止から 0.6 秒後に元の文字起こしを渡し直す。今の本番のコードを読んだ限りでは、この場合に応答が取り消されたまま戻らない（実機では確かめていない）。
- アバターの声が出たあとの発話は、新しいターンとして扱う。

`turn_end_retranscribe: true`（既定）のとき、speech.cpp には区切りごとにターン全体の音声を送る。11-02 の評価と同じ条件である。`false` にすると区間ごとの文字起こしを空白でつなぐ。

### 1.2 割り込みの判定（`TOKKIO_BARGE_IN=gated`）

今は、VAD が発話の開始を検出した時点（話し始めの約 0.2 秒後）で、内容に関係なくアバターが止まる。`gated` では、アバターが話している間だけ次のように変える。

- 発話の開始では止めない。入力側の transport の `_handle_user_interruption` を差し替え、`UserStartedSpeakingFrame` だけを流す。
- 発話が 0.6 秒続いたら（`barge_in_min_speech_s`、VAD の検出から数える）止める。話し始めから約 0.8 秒後になる。
- それより短い発話は、終わってから文字起こしを見る。相づちの一覧（`barge_in_backchannels`）にある語だけなら捨てて、アバターは話し続ける。文字起こしが空（雑音）のときも話し続ける。それ以外（「ちょっと待ってください」など）は、その時点で止めてターンとして渡す。
- アバターが話し終えたあとに文字起こしが届いた短い発話は、相づちでも通常のターンとして渡す。質問への「はい」を捨てないためである。

`TOKKIO_TURN_END=vad` のまま `gated` にすると、VAD が発話の終わりを 0.6 秒遅れて知らせるので、0.6 秒の基準を 1.0 秒に延ばして動かす。止まるのは話し始めから約 1.2 秒後になる。`gated` は `text` と一緒に使う前提で作った。

### 1.3 話し方（`TOKKIO_SPOKEN_STYLE=on`）

人物設定のプロンプトの末尾に、話し言葉の「です・ます」で答える、硬い言い回しを避ける、返答の頭に前置きを付けない、内容と数値と断り方は変えない、という指示を足す。本番は `provider: local` なので RAG の `suffix_prompt` は使われず、変えていない。

### 1.4 off のときに今と同じであること

- `bot.py` は、2 つのスイッチがどちらも既定値のとき `tokkio_turn.py` を import せず、パイプラインに何も足さない。
- 本番の controller のソースを scratch に写し、今の `.env` のまま（スイッチなし）でカスタマイザーを走らせて、本番のファイルと比べた。差は、`config.yaml` の `TurnTaking` に足したキー（既定値）、`config.py` の同じ項目、`bot.py` の 3 か所（VAD の秒数を読む式、`TurnGate` を作る条件つきの節、パイプラインの 1 行）、`tokkio_speechcpp_stt.py` に足したメソッド、新しい `tokkio_turn.py` だけだった。
- 同じ確認を、NVIDIA-ACE の `HEAD` から取り出した手つかずのソースでも行った。どちらも 2 回目の実行で結果が変わらなかった。

## 2. 言い終わり判定の評価

### 2.1 方法

11-02 の評価のデータ（`/data/ACE/turn-eval/20261102/`、VAD の区切りごとの文字起こし）に、新しい規則を当てて数えた。数え方は 11-02 と同じである。

- 途中で切った: 最後の発話区間より前でターンを確定した発話の数。
- 聞こえる切断: 切ったあと、アバターの最初の声より後に来訪者が話を再開した数。T は「判定から最初の声までの時間」から、VAD が話の再開を検出する 0.2 秒を引いた値。
- 判定までの時間: 話し終わりから判定までの無音の長さ。規則ですぐ判定したときは認識の時間を含む。

11-02 の報告とは 1 点だけ数え方が違う。11-02 は次の発話までの間が 0.2 秒未満（VAD の 6 窓、0.192 秒）の区切りを数えなかったが、実際にはそこでも VAD は止まるので、今回は数えた。11-02 と同じ数え方に戻すと、当時の数字（来訪者 13/160・14/160、FLEURS 168/650・166/650）と一致した。

### 2.2 結果（Haas）

| 音声 | 方式 | 途中で切った | 聞こえる切断 T 0.1 / 0.3 / 0.5 | 判定まで p50 / p90 / 平均（秒） | VAD の停止ですぐ判定 |
| --- | --- | ---: | ---: | ---: | ---: |
| 来訪者の質問 160 本 | 今（VAD 0.6 秒） | 11（6.9%） | 7 / 6 / 4 | 0.63 / 0.63 / 0.63 | — |
| | 11-02 の規則 | 14（8.8%） | 13 / 9 / 5 | 0.22 / 0.23 / 0.25 | 95% |
| | **今回の規則（待ち 0.6 秒）** | **6（3.8%）** | **6 / 4 / 4** | **0.22 / 0.22 / 0.23** | 97% |
| | 今回の規則（待ち 0.45 秒） | 8（5.0%） | 6 / 4 / 4 | 0.22 / 0.22 / 0.23 | 97% |
| FLEURS 650 本（読み上げ） | 今（VAD 0.6 秒） | 105（16.2%） | 76 / 52 / 28 | 0.66 / 0.67 / 0.66 | — |
| | 11-02 の規則 | 180（27.7%） | 118 / 61 / 29 | 0.25 / 0.26 / 0.25 | 99% |
| | 今回の規則（待ち 0.6 秒） | 153（23.5%） | 107 / 59 / 26 | 0.25 / 0.26 / 0.26 | 97% |

- 来訪者の質問では、判定が約 0.4 秒速くなり、切る数は今より少ない。丁寧な文末で終わる質問が 97% を占めるため、普通形を 0.6 秒待たせても全体の速さは変わらなかった。
- 上の「途中で切った」に入らない早い受け渡しが、今回の規則で 9 本ある（FLEURS は 33 本）。普通形や短い返事のあと 0.4〜0.6 秒で話が続く発話で、今の VAD はここで止まらない。今回の方式では、待ちの 0.6 秒が過ぎた時点で LLM に渡し、VAD が話の再開を知らせる 0.2 秒以内に取り消す。アバターの声が出る前なので聞こえない見込みだが、取り消しが実機で動くことが前提になる。
- 残った 6 本は、間が 1 秒を超えるもの（「はい｜お願いします」1.28〜1.92 秒、「八王子みなみ野駅から｜」1.06 秒、「すみません｜」1.06 秒）で、今の VAD 0.6 秒でも切れる。
- FLEURS では今より多く切る（16.2% → 23.5%）。読み上げの 1 文目が丁寧な文末で終わり、0.3〜0.5 秒おいて 2 文目が続く発話で、文末の規則では区別できない。来訪者が 2 文で話すと、1 文目で答え始める。取り消しと結合が効くのは、アバターの声が出る前に 2 文目が始まった場合だけである。
- Qwen3-ASR でも同じ傾向だった（来訪者 15 → 7 本、p50 0.28 秒。FLEURS 178 → 151 本）。全部の表は `/data/ACE/turn-eval/20261113/results_stored.md`。

難所セット（言いかけ 59 本、短い返事 60 本、Haas）の結果は次のとおり。

| 規則 | 言いかけをすぐ「言い終わり」と判定 | 0.6 秒待って判定 | 短い返事を VAD の停止ですぐ判定 |
| --- | ---: | ---: | ---: |
| 11-02 の規則 | 6/59 | — | 54/60 |

短い返事のうち 17 本（「はい」「いいえ」「こんにちは」など）は、0.6 秒待つようになった。これは今の本番と同じ速さである。

### 2.3 本番と同じ送り方での確認

11-02 の文字起こしは、本番が使う `chunking_strategy=auto` と登録語なしで作られていた。そこで Haas を本番と同じ送り方（VAD モデル、登録語「青嵐」、`chunking_strategy=auto`）で CPU（4 スレッド）で動かし、来訪者の質問と難所セットを書き起こし直した。

- 文末の種類が 11-02 の文字起こしと変わった区切りは、来訪者 1/285、難所 1/140。来訪者の質問の結果は上の表と同じだった（6/160、p50 0.22 秒）。
- 区間ごとの文字起こしをつないだ場合（`turn_end_retranscribe: false`）も、文末の種類が変わったのは来訪者 0/285、難所 1/140 で、結果は同じだった。
- 文字起こしが空になった区切りはなかった。
- 認識の時間は CPU の値（p50 0.30 秒）なので使っていない。表の時間は 11-02 の GPU での値で計算した。

### 2.4 判定のあとに足される時間

判定から先は今と同じで、集約の待ち 0.05 秒、RAG と LLM の最初の句、TTS の最初の音声が続く。11-13 の実測（`kagawa-live-latency` の記録）では、文字起こしから TTS の開始までが 0.18〜0.36 秒だった。この値からは、T は 0.1〜0.3 秒に当たる。11-02 の報告が想定した 0.3〜0.5 秒より短く、切断が聞こえやすい側になる。

## 3. 割り込みの確認

音声を使った評価はしていない。相づちの録音と、アバターの声がマイクに回り込む音声が手元にないためである。確かめたのは次の 2 つ。

- pipecat 0.0.68 を scratch の venv に入れ、実物の入力 transport、集約器、割り込みの仕組みの上で `TurnGate` を動かした（`infra/tests/test_tokkio_turn_pipecat.py`、15 本）。相づちと雑音では止まらないこと、短い発話は文字起こしの時点で止まること、長い発話は基準の時間で止まること、止めたあとの文字起こしが 1 回だけ LLM に渡ることを確かめた。
- 難所セットの短い返事 60 本を本番と同じ送り方で書き起こし、相づちの判定に通した。相づちと判定したのは「はい」「なるほど」の 7 本で、「いいえ」「お願いします」「結構です」などは相づちと判定しなかった。

分かっている弱点は次の 3 つ。

- Haas は「うん」を「あうん。」「む」と書くことがあった。この書き方は一覧にないので、アバターは止まる。
- アバターは、animation graph が 1 文の再生を終えるたびに「話し終えた」と知らせ、次の文で「話し始めた」と知らせる。その間に発話の開始が来ても割り込みを保留できるよう、話し終えてから 0.3 秒は話している扱いにした。0.3 秒で足りるかは実機で確かめる必要がある。
- 止まるまでの時間は、今の約 0.2 秒から、長い発話で約 0.8 秒、短い発話で「発話の長さ＋0.25 秒」ほどに延びる。

## 5. アバターからの相づち（実装していない）

来訪者が話している途中にアバターが「はい」「ええ」と声を出す機能は、今回は入れなかった。理由は次のとおり。

- 相づちの声を出すと animation graph が「話し始めた」と知らせ、今の仕組みではそれが応答の開始と区別できない。取り消しと結合の判定（声が出る前かどうか）と、割り込みの判定（アバターが話しているかどうか）の両方が狂う。
- 相づちの声がマイクに回り込むと、VAD が来訪者の発話として拾い、文字起こしに混ざるおそれがある。回り込みの量は実機でしか分からない。
- 打つ時点を決める材料は、今は VAD の区切りと文字起こししかない。0.2 秒の区切りで「続きがある形」と判定した直後に打つ方法が考えられるが、認識と TTS を合わせると発話の切れ目から 0.4 秒ほど遅れ、来訪者の次の言葉に重なりやすい。

先に試すなら、声を出さない相づち（うなずきのジェスチャー）がよい。`TurnGate` が「続きがある形」と判定した時点でジェスチャーのフレームを出すだけで済み、上の 3 つの問題が起きない。Tokkio の場面にうなずきのクリップがあるかは確かめていない。

| 確かめること | 聞く・見るところ |
| --- | --- |
| `text`: 丁寧な質問への応答が速くなるか | 「〜ですか」「〜ください」のあと、今より約 0.4 秒早く声が出るか。controller のログの `Turn end (rule, complete)` の秒数 |
| `text`: 考えながら話しても切られないか | 「えっと、」「〜なんですけど、」のあとで 0.8 秒待つか。「AIを使った、非破壊検査の…」のように普通形のあとで間を置いたとき |
| `text`: 2 文で話したとき | 「見学したいです。いつですか。」で、1 文目への応答の声が出てしまうか。出る前に取り消されたときはログに `Turn taken back` が出る |
| `text`: 「はい」「そうですね」だけの返事 | 0.6 秒・0.8 秒の待ちが遅く感じるか |
| `text`: 取り消しのときに声の頭が漏れないか | 応答の最初の音だけが聞こえて止まる、ということがないか |
| `gated`: 相づちで止まらないか | アバターが話している間に「うん」「はい」「なるほど」と言う。ログの `Backchannel while the avatar speaks` |
| `gated`: 止めたいときに止まるか | 「ちょっと待ってください」「すみません、」と話しかけて、止まるまでの長さが許せるか。ログの `Barge-in on transcript` と `Barge-in after` |
| `gated`: アバターの声の回り込み | スピーカーで使ったとき、アバター自身の声で止まらないか。今は回り込みがあればすぐ止まるので気づけるが、`gated` では文字起こしが LLM に渡ってから気づくことになる |
| `gated`: 文と文の間 | 返答の 2 文目が始まる瞬間に相づちを打ったとき、止まってしまわないか |
| 話し方 | 「〜ですよ」「〜ですね」が多すぎないか。数値の言い方（「25万円」）を TTS が正しく読むか |

## 7. 限界

- 実マイク、実際のブラウザ、Tokkio の本物のパイプライン（ACE の transport、A2F、animation graph）では動かしていない。`bot.py` の書き換えは構文の確認までで、実行していない。pipecat の試験で使ったアバター役と LLM 役は代役である。
- 文末の規則は、11-02 の評価で切れた発話を見てから直した。同じデータで数え直しているので、独立した検証ではない。来訪者の質問は合成音声で、丁寧な問いかけが中心である。くだけた話し方の来訪者は 0.6〜0.8 秒待つことになり、今より速くはならない。
- VAD を 0.2 秒にすると、認識の要求が増える（11-02 の計測で 1 ターン平均 1.78 回）。ターン全体を送り直すので、長い発話ほど 1 回の音声が長くなる。上限は 30 秒で、超えたら最後の区間だけを送る。本番の GPU0 での認識時間は測っていない。
- 英語モード（`QwenTTSService`）では、3 つのスイッチを on にしても off として設定を作る。規則と一覧が日本語用のためである。
- 録音の途中に文字起こしが空の区間（雑音）があっても、次のターンの音声に混ざらないようにした（新しいターンの始まりでターンの音声を捨てる）。pipecat の試験で確かめたが、実際の雑音では確かめていない。
- `TurnTaking.vad_stop_secs` を使う Riva（`RivaASRService`）との組み合わせは確かめていない。Riva にはターン全体を送り直す仕組みがないので、`text` にすると区間ごとの文字起こしをつなぐ動きになる。

## 9. 配備するときの注意

- スイッチが off のままでも、次の `manage_tokkio.sh start` または `sync-controller` で、書き換えた `bot.py`、`config.py`、`tokkio_speechcpp_stt.py` と新しい `tokkio_turn.py` が controller に入る。off のときはこれらの新しい部分を通らないが、コードそのものを前の状態に戻すには、`.env` の値ではなくリポジトリのファイルを戻す必要がある。
- 3 つのスイッチは、カスタマイザーが作る controller の `configs/config.yaml` に入り、`sync-controller` が pod の `/code/configs/config.yaml` に写す。`workspace/controller/ace-app-config.yml` は配備先の構成を書くファイルで、スイッチとは関係がない。
- systemd が直接実行するファイル（`infra/tts/`、`infra/asr/` の起動スクリプトと `irodori_server.py`）は変えていない。

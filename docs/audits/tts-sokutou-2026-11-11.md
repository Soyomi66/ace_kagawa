# TTS エンジン sokutou と現行 speech.cpp の比較（2026-11-11）

自作の推論エンジン sokutou（[kosuketut/sokutou](https://github.com/kosuketut/sokutou)、main の 68b871c）を、本番の Irodori-TTS（speech.cpp v0.8.7）と比べた。どちらも同じ Irodori-TTS v4.1-Small の重みを使う。比べたのは速さ、本人らしさ、読み、抑揚、GPU メモリー、起動時間で、caption の違いは聞き比べに回した。

本番の unit、Tokkio、`.env` は変更していない。計測のあいだ本番の Irodori は止まっていた（こちらでは起動も停止もしていない）。aituber の本番が使う GPU1 にも触れていない。

## 結論

**同じ 12 steps で比べると、sokutou は 1 文の合成が約 0.08 秒速い。** 中央値は短い文で現行の 0.117 秒から sokutou の 0.038 秒（3.1 倍）、長い文で 0.189 秒から 0.106 秒（1.8 倍）になった。倍率は文の長さで変わるが、縮む時間はどちらも約 0.08 秒だった。このうち約 0.01 秒は caption を外した分で、caption なしの speech.cpp と比べたエンジンどうしの差は約 0.07 秒である。

**本人らしさと読みは、エンジンによる差が見つからなかった。** sokutou は同じ seed で公式の実装（PyTorch、fp32）とほぼ同じ波形を出す（相関の中央値 0.999）。本人らしさの差の 95% 区間は 0 をまたぐ。

**ただし、sokutou のサーバーをそのまま使うと、読点で終わる文の語尾が乱れる。** サーバーは「、」で終わる文に「。」を足すため、「私は複合材料、」が「私は複合材料、。」になる。この文を 30 通りの seed で合成すると、Whisper は 30 本中 5 本で、語尾に「を」などの余計な音を聞き取った（現行は 0 本）。本番では返答の最初の読点で文を切って先に合成するので、この形の文はよく出る。sokutou の `server/server.py` で「、」を文末の記号（`TERMINATORS`）に加えると 0 本になった。導入する前に、この 1 行を直す必要がある。

**caption（話し方の指示文）は sokutou で使えない。** caption は、本番の参照音声が原稿の読み上げ調で、返答がどれも読み上げのように聞こえたため、10/17 に入れたものである。10/18 の監査と同じく、F0 の揺れでは caption の有無の差が出なかった。caption がなくてよいかは、聞いて決める。

**導入の前に確かめることが 3 つある。**

- GPU メモリーが 2.5 GB から 12.4 GB に増える。本番の GPU0 には vLLM（約 26 GB）、A2F、Riva も載る。収まるかは Tokkio を動かした状態で確かめていない。
- GPU0 を vLLM などと共有したときの速さを測っていない。10/17 に本番で測った TTS の最初の音声は中央値 0.39 秒で、GPU が空いているときの 0.24 秒より遅かった。GPU の共有が原因と疑われているが、確かめてはいない。共有した状態で sokutou の速さがどうなるかも分からない。
- 12 steps は sokutou の README が確かめた範囲（20 と 40）の外にある。今回は 12 steps で 337 回（起動のときの試し合成を含む）合成し、エンジンが公式の関数に戻った合成（`irregular_requests`）は 0 回だった。読みと本人らしさも 20 steps と同じだった。

利用者が待つ時間が縮むのは、返答の最初の 1 文の分だけである。2 文目からは、1 文目を再生しているあいだに合成が終わるためである（`docs/audits/tts-alternatives-2026-10-17.md`）。

### 条件

- 文は 15 文。10/17 の会話で TTS に渡った本番の 10 文（10/18 の監査と同じ）と、10/17 の比較で使った 5 文（短文、専門、アクセス、数字、長文）。
- 両方のエンジンに同じ文と長さを送った。要求は、本番の unit の設定を本番のサーバーの関数に渡して作った。読みを正規化した後に 😊 を付け、16 字以下の文には話す長さ（`seconds`）を指定する。16 字以下の文は 8 文、それより長い文は 7 文。
- seed は 1〜6 で、各構成 90 回。計測の前に、全文を 1 巡ずつ合成してウォームアップした。seed が同じでも、speech.cpp と sokutou では乱数が違うので、エンジンをまたいで音声を対にはしていない。
- GPU0（RTX 6000 Ada）では一度に 1 つの構成だけを動かした。計測中は GPU0 で動くプロセスを毎秒記録し、自分が起動した 1 つだけだったことを確かめた。
- speech.cpp は本番と同じ worker を直接呼んだ（`--device Vulkan1`、`--threads 8`、CPU で作った声のファイル）。時間は要求を送ってから最後のチャンクが届くまで。
- sokutou は GitHub の main から自前のタグでイメージを作り、Docker で動かした。声は本番と同じ 33 秒の参照 WAV で、起動のときに GPU で潜在変数にする。出力は 48 kHz にした。時間は HTTP で送ってから応答を受け取るまで。サーバーが返す合成時間（`X-Synthesis-Seconds`）との差は、中央値で 0.003 秒だった。
- 採点の前に、すべての音声に本番の出力段（16 kHz、前後の無音の切り落とし、フェード、−0.5 dB）をかけた。
- 採点は 10/18 の監査と同じ方法で行った。本人らしさは CAMPPlus の埋め込みの cosine で、本番の参照と本人の別の録音の 2 つと比べた（2 つの録音どうしは 0.87）。読みは Whisper large-v3-turbo の書き起こしと元の文の CER、抑揚は pyin の F0 の標準偏差（半音）で測った。

| 構成 | 全体 p50 | 全体 p90 | 短い文 p50 | 長い文 p50 | 最長の文（「東京工科大学では…」） | GPU メモリー |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P-caption（現行） | 0.162 秒 | 0.211 秒 | 0.117 秒 | 0.189 秒 | 0.317 秒 | 2,501 MiB |
| P-nocap | 0.151 秒 | 0.194 秒 | 0.107 秒 | 0.178 秒 | 0.287 秒 | 2,463 MiB |
| **S12** | **0.045 秒** | **0.116 秒** | **0.038 秒** | **0.106 秒** | **0.168 秒** | 12,392 MiB |
| S20 | 0.057 秒 | 0.140 秒 | 0.049 秒 | 0.127 秒 | 0.207 秒 | 12,402 MiB |
| 参考: v0.10.1 | 0.166 秒 | 0.218 秒 | 0.120 秒 | 0.195 秒 | 0.338 秒 | 2,501 MiB |

- 長い文では倍率が下がる。時間の内訳（DiT、復号、切り落とし）は測っていない。
- caption を付けると 0.011 秒遅くなる（P-caption と P-nocap の差）。caption なしどうし（P-nocap と S12）で比べると、中央値は短い文で 0.107 秒から 0.038 秒、長い文で 0.178 秒から 0.106 秒になる。
- speech.cpp v0.10.1 は v0.8.7 より速くならなかった。音声は 90 本すべてが v0.8.7 とバイト単位で同じだった。
- S20 の全体の中央値 0.057 秒は、sokutou の README の値（20 steps で 0.059 秒）とほぼ同じだった。
- 起動は、sokutou が毎回 28〜30 秒かかった（うちエンジンの準備は 8.5 秒）。speech.cpp はこの日の最初の起動が 28 秒、2 回目からは 1.1 秒だった。

## 本人らしさ・読み・抑揚

| 構成 | 本人らしさ（本番の参照 / 別の録音） | 現行との差（別の録音）[95% 区間] | CER | CER が 0.2 を超えた回数 | F0 の揺れ（半音） |
| --- | --- | --- | ---: | ---: | ---: |
| P-caption（現行） | 0.642 / 0.575 | — | 0.023 | 0/90 | 3.06 |
| P-nocap | 0.654 / 0.592 | +0.018 [+0.004, +0.030] | 0.023 | 0/90 | 2.97 |
| S12 | 0.644 / 0.582 | +0.007 [−0.008, +0.021] | 0.041 | 2/90 | 2.93 |
| S20 | 0.649 / 0.584 | +0.009 [−0.006, +0.026] | 0.049 | 2/90 | 2.96 |

- 95% 区間は文ごとに seed の平均をとり、15 文を 5,000 回再標本化して出した。
- 本人らしさは sokutou と現行で差が見えなかった。caption を外すと、本人らしさはわずかに上がった。caption の狙いは話し方を参照音声の読み上げ調から離すことなので、この向きは狙いと合う。
- F0 の揺れはどの構成でも現行との差の区間が 0 をまたいだ。抑揚の違いは聞いて判断する。
- CER が 0.2 を超えた 2 回は、S12 と S20 で同じ文と seed の組だった。「私は複合材料、」の seed 4 と、「私は香川ゆたかです。」の seed 5 である。sokutou は steps が違っても、同じ seed なら同じ乱数から合成を始める。そのため、独立した 4 回の失敗ではない。

### 読みの崩れの切り分け（2 文 × 30 seeds）

| 構成 | 「私は複合材料、」で語尾に余計な音 | うち大きく崩れた回数 | 「私は香川ゆたかです。」の誤り |
| --- | ---: | ---: | ---: |
| 現行 speech.cpp | 0/30 | 0 | 1/30 |
| speech.cpp に「私は複合材料、。」を送る | 7/30 | 0 | — |
| 公式の実装（「。」を足す） | 3/30 | 0 | 1/30 |
| sokutou 12 steps（「。」を足す） | 5/30 | 1 | 1/30 |
| **sokutou 12 steps（「、」で止める）** | **0/30** | 0 | 1/30 |

- 余計な音は Whisper の書き起こしでは「私は複合材料を」「私は複合材料単」と出た。speech.cpp でも「、。」を送ると同じことが起きたので、エンジンではなく文の終わりに付いた「。」が原因である。
- sokutou と公式の実装は同じ seed で波形の相関の中央値が 0.999（「私は複合材料、」）と 0.998（「私は香川ゆたかです。」）だった。sokutou は公式の実装をほぼそのまま再現している。60 本中 6 本は相関が 0.95 を下回り、うち「私は香川ゆたかです。」の seed 7 と 21 は相関がほぼ 0 で、長さも違った（2.14 秒と 2.40 秒、2.17 秒と 2.22 秒）。この 6 本でも、書き起こしは公式の実装と同じだった。
- 大きく崩れた 1 回（seed 4、書き起こしは「私は福岡を在りを」）は、公式の実装の同じ seed との相関が 0.998 で、公式の実装のほうは正しく書き起こされた。ほぼ同じ音声で Whisper の判定が分かれたので、エンジンの劣化を示すものとは言えない。聞いて確かめる（聞き比べページの 2 つ目の表）。
- 「ゆたか」が「ゆか」に聞こえる誤りは、現行を含むすべての構成で 30 本中 1 本ずつあった。sokutou によるものではない。
- 直すには、sokutou の `server/server.py` の `TERMINATORS` に「、」を加える。今回は評価用のコンテナに直したファイルを差し込んで確かめただけで、sokutou のリポジトリは変えていない。

## 導入するときの前提

- **caption を使えない。** sokutou の README の「できないこと」に書かれている。😊 は文の一部なので使える。
- **1 つのサーバーで声は 1 つ。** kagawa は声が 1 つなので問題ない。
- **Docker で動かす。** 今の unit は Python の venv で speech.cpp の worker を動かしているので、systemd の unit か compose の定義を新しく作る必要がある。
- **今のサーバーの機能を残すなら、backend として足す形になる。** 読みの正規化、😊、短い文の長さの上限、短文のキャッシュ、出力段は `infra/tts/irodori_server.py` にある。sokutou を backend の 1 つとして HTTP で呼べば、これらはそのまま使える。実装はしていない。
- **電子透かしはどちらの音声にも入らない。** speech.cpp は入れず、sokutou は既定で外す。
- **参照音声の扱いが違う。** speech.cpp は CPU で作った声のファイルを使い、sokutou は起動のたびに 33 秒の WAV を GPU で潜在変数にする。speech.cpp では GPU で作った声のファイルで本人らしさが下がったことがあるが、今回の sokutou では下がらなかった。

## 次に確かめること

1. 聞き比べで、caption がなくても話し方がよいかを決める。
2. Tokkio を動かした状態で GPU0 の空きメモリーを確かめ、sokutou の 12.4 GB が収まるかを見る。
3. vLLM が生成しているあいだの TTS の遅延を、speech.cpp と sokutou で比べる。
4. 採用するなら、sokutou の `TERMINATORS` に「、」を加え、`irodori_server.py` に sokutou の backend を足す。

## ファイル

作業一式は `/data/ACE/irodori/benchmarks/20261111_sokutou/` にある。

- `index.html`: 聞き比べページ。ブラインド比較（現行と sokutou 12 steps、15 組）、「、」の扱いの比較、全構成の表がある。ブラインド比較の「私は複合材料、」の組だけは、sokutou 側に「、」で止めるように直したサーバーの音声を使った。左右の割り当ては `blind_key.json` にある。
- `cases.json`: 15 文と、本番の unit から作った要求。

- `post16k/`、`post16k-extra/`: 本番の出力段を通した音声。
- `scores.jsonl`、`scores_extra.jsonl`、`latency.json`、`latency_groups.json`、`quality.json`: 採点と集計。
- `scripts/`: `make_cases.py`、`bench_speechcpp.py`、`bench_sokutou.py`、`postprocess.py`、`evaluate.py`、`latency.py`、`quality.py`、`make_page.py`。
- `src/`: 計測に使った sokutou の clone（main の 68b871c）。`patched/server.py` は「、」を加えた評価用の `server.py`。
- `voices/kagawa/ref.wav`: 本番の参照音声の写し。

Docker のイメージは `ace-kagawa-eval/sokutou-server:68b871c` と `ace-kagawa-eval/sokutou-official:68b871c` を作った。中身は利用者が作った `sokutou/*` と同じ層で、`sokutou/*` のタグは変えていない。評価用のコンテナはすべて止めて消した。
